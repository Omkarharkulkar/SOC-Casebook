# CASE-002 — Suspicious Windows Process Execution

- **Status:** Analysis complete
- **Investigation type:** Two-source Windows process-creation analysis
- **Part A:** Local Windows Security events
- **Part B:** Public Sysmon EVTX sample
- **Part B detection:** Medium
- **Overall verdict:** Suspicious process execution observed in public evidence; compromise not confirmed
- **Analyst:** Omkar Harkulkar

## 1. Overview

This case examines Windows process-creation activity using two separate evidence sources.

Part A uses four Windows Security Event ID 4688 records collected from my own Windows PC during normal activity.

Part B uses a public Sysmon EVTX sample from the EVTX-ATTACK-SAMPLES repository. Hayabusa generated a medium-level detection related to FTP-based command execution.

The two sources are analysed separately because they come from different systems and collection contexts.

Part A provides a small baseline of ordinary process activity. Part B contains suspicious process activity that requires further investigation.

Neither source provides sufficient evidence to confirm system compromise.

## 2. Objective

- Collect and review process-creation events from my own Windows PC.
- Analyse a separate public Windows event-log sample.
- Identify process names and parent-child relationships.
- Review the detection generated by Hayabusa.
- Compare the findings without mixing evidence sources.
- Document suitable SOC L1 investigation steps.

## 7. Detection Analysis

**Detection:** Potential Arbitrary Command Execution Via FTP.EXE

- Detection source: Hayabusa built-in Sigma rule
- Rule ID: `086262f5-1aee-ce11-2ddf-4692b9e51b3e`
- Severity: Medium
- Rule status: Test
- Event record: 16513
- Event ID: 1

The rule checks Windows process-creation activity involving FTP and its parent-child process relationships.

For record 16513, the match was through the rule's FTP parent-process condition. The event shows FTP as the parent of Command Prompt.

The rule is labelled `test` in its metadata. Its alert is an investigation lead, not proof of compromise.

## 8. Combined Findings

1. Part A contains four local Windows Security process-creation records.
2. Part A includes activity consistent with the audit-policy and identity checks performed during collection.
3. Part A also includes two Windows management/service-related process records whose full context was not established.
4. Part B contains four public Sysmon process-creation events.
5. Hayabusa generated a medium-level FTP-related alert for public sample record 16513.
6. The public alert matched through the FTP parent-process condition.
7. The local and public evidence come from different systems and must not be treated as one timeline.
8. Neither evidence source establishes successful file transfer, payload execution, or system compromise.

## 9. Verdict and Reasoning

**Verdict: Suspicious process execution observed in the public sample — further investigation required.**

Part A provides a limited baseline of process-creation activity from my own Windows PC. The collected records are consistent with the checks performed and Windows service-related activity.

Part B contains a suspicious process sequence and a medium-level FTP-related detection. This warrants further investigation if similar activity is found in a production environment.

The two sources are independent. The public sample does not represent activity on my own PC, and the local sample does not validate the public sample's behaviour.

There is no evidence in the reviewed records to confirm successful file transfer, persistence, data access, or system compromise.

## 10. Recommended SOC L1 Actions

If similar activity appeared in a production environment:

1. Preserve the relevant Windows Security and Sysmon event logs.
2. Review the full process tree, including parent and child process details.
3. Examine surrounding network, file, and authentication events.
4. Check whether the process activity was expected and authorised.
5. Search for related activity on other hosts and accounts.
6. Escalate to the appropriate security team if corroborating evidence is found.
7. Follow the organisation's incident-response policy when deciding whether containment is necessary.

Do not treat a detection alone as sufficient justification for a confirmed-compromise conclusion.

## 11. Limitations

- Part A contains only four selected Event ID 4688 records.
- Part A is a sanitised CSV export, not the original Windows event log.
- The local collection represents a short period of activity, not a complete system history.
- Part B uses one public EVTX sample, not a capture from my own Windows PC.
- The original context of the public sample was not independently verified.
- The public sample contains only four Sysmon process-creation events.
- The Hayabusa detection rule is marked `test`.
- No additional endpoint, network, or authentication telemetry was available for correlation.
- The reviewed evidence does not establish successful file transfer, payload execution, or system compromise.

## 12. Conclusion

This case used two separate evidence sources to investigate Windows process creation.

Part A demonstrated how Windows Security Event ID 4688 records can be collected and reviewed using PowerShell. The small sample provided a baseline of ordinary process activity from my own PC.

Part B demonstrated how Hayabusa can analyse a public Sysmon EVTX sample and identify suspicious FTP-related process activity through a built-in Sigma detection.

The findings show why process relationships and surrounding context matter during SOC L1 investigation. A detection provides a lead, but additional evidence is needed before concluding that an incident resulted in compromise.
