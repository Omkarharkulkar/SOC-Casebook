## Case Summary

This investigation analyzed a network capture containing DNS, HTTP, TLS, SMB2 and DCE/RPC traffic. Routine connectivity and update-related activity was observed alongside suspicious internal SMB file operations and remote Service Control Manager activity.

The investigation identified 11 SMB CREATE requests and 11 corresponding WRITE requests involving `q4-summary.bin`. All WRITE requests were 96 bytes and received successful SMB responses.

Further analysis identified two correlated SCM waves initiated by HOST-1 (`10.42.10.21`) involving the same six destinations. Each wave contained the sequence `ROpenSCManagerW`, `RCreateServiceW` and `RStartServiceW`, correlated by TCP stream and DCE/RPC call ID.

During the first wave, `WinHostSvc` was created across six destinations using a command-interpreter binary path. All service-creation responses returned `WERR_OK`; all service-start responses returned `WERR_SERVICE_REQUEST_TIMEOUT`.

During the second wave, `WinUpdateSvc` was created across the same six destinations using a binary located in the Windows Temp directory. All service-creation and service-start responses returned `WERR_OK`.

The repeated SMB operations, multi-host service-control sequences and timing support an inference of coordinated or automated remote activity.

**Final assessment:** Suspicious remote service execution and lateral movement observed — escalate to L2 for validation.

The investigation is network-only. It does not establish authorization, operator identity, successful endpoint execution or confirmed compromise.

### 6.3 CREATE Operation Results

The 11 CREATE requests used disposition value `1`, corresponding to `FILE_OPEN`.

All 11 corresponding CREATE responses returned status:

`0x00000000`

This indicates successful SMB-level completion of the CREATE requests.

The result should not be interpreted as proof that a new file was created. The disposition indicates an open-existing-file operation.

### 6.4 WRITE Operations

Eleven WRITE requests were identified on the same TCP streams as the corresponding `q4-summary.bin` CREATE requests.

Each WRITE request transferred 96 bytes.

| Result | Count |
|---|---:|
| WRITE requests | 11 |
| WRITE responses with status `0x00000000` | 11 |
| Total requested write length | 1,056 bytes |

The WRITE operations were matched to the corresponding CREATE operations using both Tree ID and File ID.

This provides stronger evidence than matching only by filename or TCP stream.

The observed responses indicate successful SMB-protocol-level WRITE operations. They do not establish the content, purpose, or authorization of the written data.

### 6.5 SMB Assessment

The repeated use of an administrative share, the two bursts of file access, and the associated successful WRITE operations are suspicious in the context of the later remote service-management activity.

This behavior is consistent with remote administration or lateral movement patterns. However:

- The file content was not established by the network metadata reviewed.
- The file's purpose is unknown.
- The activity may have been authorized administrative or red-team activity.
- The relationship between `q4-summary.bin` and the later service operations is not established.

The file should not be described as a confirmed payload or executable based on the available evidence.

The presence of service creation and start operations is relevant to remote service execution analysis.

### 7.3 Correlation Method and Example

SCM requests and responses were correlated using TCP stream and DCE/RPC call ID. The operation sequence was then compared across destinations.

HOST-2 (`10.42.10.22`) is one example of the correlated activity, not the only destination.

During the first wave, HOST-2's TCP stream 193 contained:

| Operation | Request frame | Response frame | Call ID |
|---|---:|---:|---:|
| ROpenSCManagerW | 3073 | 3074 | 2 |
| RCreateServiceW | 3079 | 3085 | 3 |
| RStartServiceW | 3086 | 3088 | 4 |

The same operation sequence was identified on five additional destinations during the first wave and across all six destinations during the second wave.

Overall, 12 complete SCM sequences were correlated: six destinations across two waves.

**Evidence:** E-004 and E-007.

### 7.4 Service Definitions

Two service binary paths were identified in the service-management evidence:

**WinHostSvc**

`C:\Windows\System32\cmd.exe /Q /c whoami > C:\Windows\Temp\svc.out 2>&1`

**WinUpdateSvc**

`C:\Windows\Temp\WinUpdateSvc.exe`

The `WinHostSvc` definition uses `cmd.exe` to run a command that requests the current user identity and redirects the output to a temporary file.

The `WinUpdateSvc` definition references an executable under the Windows temporary directory.

These service definitions are suspicious in context and warrant endpoint validation. The capture does not establish whether either binary was present on disk, whether the commands completed, or what process activity occurred on the destination systems.

### 7.5 Interpreting the Service-Start Timeout

The `WinHostSvc` binary path invokes `cmd.exe` rather than a conventional Windows service executable.

A service-start timeout can occur when a command-interpreter process does not behave like a normal service process and does not report the expected service status to the Service Control Manager.

Therefore, the timeout is compatible with a service-control interaction involving a command interpreter. It does **not** prove that the command failed to run.

Endpoint process telemetry and the output file would be required to determine whether the command actually executed and completed.

### 7.6 Correlated Multi-Host Service Control Activity

The SCM operations CSV and decoded packet details establish two repeated service-control waves initiated by HOST-1 (`10.42.10.21`). Each wave covers the same six destinations: HOST-2 (`10.42.10.22`) and five systems in the `10.42.20.0/24` network.

For every destination in both waves, the packet sequence contains:

1. `ROpenSCManagerW` — opnum 15, call ID 2.
2. `RCreateServiceW` — opnum 12, call ID 3.
3. `RStartServiceW` — opnum 19, call ID 4.

Each request and corresponding response was correlated using its TCP stream and DCE/RPC call ID. This establishes 12 complete SCM sequences across the two waves.

**Wave 1 — 19:57:48 IST**

The service created on all six destinations was `WinHostSvc`, with the binary path:

`C:\Windows\System32\cmd.exe /Q /c whoami > C:\Windows\Temp\svc.out 2>&1`

All six service-creation responses returned `WERR_OK`. All six service-start responses returned `WERR_SERVICE_REQUEST_TIMEOUT (0x0000041d)`.

**Wave 2 — 20:02:07 IST**

The service created on all six destinations was `WinUpdateSvc`, with the binary path:

`C:\Windows\Temp\WinUpdateSvc.exe`

All six service-creation responses and all six service-start responses returned `WERR_OK (0x00000000)`.

The repeated operation order, six-host scope, tightly grouped packet timing, and recurrence approximately four minutes apart support an inference of coordinated or automated remote service-control activity.

The first wave's service-start timeout does not establish that the command did not execute. Similarly, the successful responses in the second wave do not independently establish that the binary executed successfully or produced its intended effects. Endpoint process and service telemetry would be required to confirm execution and impact.

The evidence therefore supports suspicious remote service creation and start activity across six destinations. It does not establish authorization, operator identity, persistence, or confirmed endpoint compromise.

Per-destination service names, binary paths, CREATE responses, START requests and START responses are recorded in `analysis/part-b/scm-service-correlation.csv`. The artifact contains the frame references and TCP stream for all 12 sequences, allowing the observations to be checked against the original PCAP.

**Evidence:** E-004 and E-007.

### 7.7 Account Attribution

The reviewed NTLM username extraction did not return usable account attribution.

The source and destination IP addresses are known from the capture, but the responsible user account has not been established.

### 7.8 Relationship Between SMB and Service Activity

The SMB file operations and the service-management activity both involve HOST-1 as a source.

However, the capture does not establish that `q4-summary.bin` was used as the executable or payload for either service.

The SMB file activity and the remote service operations are therefore treated as separate suspicious observations within the same investigation.

A file-to-service execution chain has not been confirmed.

## 10. Detection Hypotheses

The following detection ideas could help identify similar behavior in a SOC environment.

### Hypothesis 1 — Repeated Administrative Share File Operations

Alert or investigate when a single workstation performs repeated SMB file operations against administrative shares across several internal destinations within a short period.

Potential fields:

- Source IP
- Destination IP
- Share name
- Filename
- SMB CREATE and WRITE operations
- Number of distinct destinations
- Time between activity bursts

### Hypothesis 2 — Remote Service Creation and Start

Investigate remote Service Control Manager activity when a host creates and starts services on multiple internal systems.

Potential indicators:

- `RCreateServiceW`
- `RStartServiceW`
- Source and destination host
- Service name
- Service binary path
- Service-start response status

### Hypothesis 3 — Unusual Service Binary Paths

Review newly created services whose binary paths reference:

- Command interpreters such as `cmd.exe`
- Executables under temporary directories
- Unusual scripts or command-line arguments
- Paths inconsistent with the expected service inventory

### Hypothesis 4 — Combined SMB and Remote Service Activity

Prioritize investigation when the same source host performs administrative-share file operations and remote service-management operations against internal systems.

This combination can be useful for lateral movement detection. However, the events should be correlated using timestamps, host identifiers, and available endpoint telemetry rather than assuming that file access automatically led to service execution.

## 11. Severity and Escalation Decision

### Recommended Priority: High

The case is recommended for High-priority L2 validation because the capture contains multiple suspicious behaviors:

- Repeated SMB administrative-share access from HOST-1.
- Eleven successful SMB CREATE operations for the same filename.
- Eleven associated successful WRITE operations.
- Activity across six destination IP addresses.
- Remote Service Control Manager create/start operations.
- A service definition invoking `cmd.exe` with a `whoami` command.
- A second service definition referencing an executable under a temporary directory.

The combination is consistent with possible remote administration abuse or lateral movement.

### Why This Is Not a Confirmed Compromise

The evidence is network-only. It does not confirm:

- Whether the activity was authorized.
- Whether the operator was an attacker or administrator.
- Whether the service binaries existed on disk.
- Whether the service commands completed successfully.
- Whether `q4-summary.bin` was malicious or related to the services.
- Whether persistence was established.
- Whether any endpoint was actually compromised.

### Escalation Recommendation

Escalate to L2 for:

1. Endpoint process telemetry from HOST-1 and HOST-2.
2. Windows Service Control Manager event logs.
3. Service installation and configuration history.
4. File-system validation for `q4-summary.bin` and the referenced service binaries.
5. Account and authentication log correlation.
6. Change-management or administrative activity records.
7. Confirmation of whether the activity was part of an authorized red-team exercise or administrative task.

## 12. What Could Change the Assessment?

The main alternative explanation is an authorized red-team exercise, penetration-testing activity, or legitimate administrative operation.

If the system owner confirms that the SMB and remote service-management activity was approved and performed within the expected scope, the assessment may be downgraded.

If endpoint telemetry confirms unauthorized service creation, unexpected process execution, or malicious file activity, the assessment may be strengthened and the incident handled as a confirmed endpoint compromise.

The current capture alone cannot distinguish these explanations.

## 13. Limitations

This investigation has several limitations:

1. **Network-only evidence:** No endpoint process logs, Windows event logs, or host forensic artifacts were available for this analysis.

2. **Simulated alert:** The alert is a case-study scenario, not a live alert generated by the dataset publisher or an operational IDS/SIEM.

3. **Unresolved checksum discrepancy:** The local PCAP hash matches the publisher checksum file, but the dataset webpage displays a different SHA-256 value. The discrepancy has not been resolved.

4. **Synthetic DNS-to-SMB inconsistency:** `files.arden.local` consistently resolves to `10.42.20.40`, while SMB requests using that UNC hostname are directed to six different destination IPs. The dataset's reason for this behavior is unknown.

5. **No account attribution:** The reviewed authentication data did not establish the responsible user account.

6. **Service execution not confirmed:** Service-management responses establish protocol-level outcomes, not endpoint process completion.

7. **Timeout interpretation:** The `WERR_SERVICE_REQUEST_TIMEOUT` response does not prove that the associated command failed to execute.

8. **No confirmed file-to-service relationship:** The capture does not establish that `q4-summary.bin` was used by the observed services.

9. SCM requests and responses were correlated across all six destinations in both waves using TCP stream and DCE/RPC call ID. Service names, binary paths and response results were extracted from decoded packet details and are documented in the supplementary SCM correlation evidence.

Although the network responses establish the observed SCM-level results, they do not independently prove successful endpoint process execution or the intended effects.

10. **No dataset ground truth:** No authoritative answer key was available to confirm the intended interpretation of the synthetic scenario.

11. **Encrypted traffic:** TLS application content was not inspected.

12. **Baseline limitations:** Part A provides a short controlled DNS/HTTPS baseline. It is not representative of normal enterprise traffic and should not be used as a complete benign-behavior model.

## 14. Final Conclusion

The network capture contains suspicious SMB file operations and repeated remote Service Control Manager activity originating from HOST-1 (`10.42.10.21`).

The investigation identified 11 SMB CREATE requests and 11 corresponding WRITE requests involving `q4-summary.bin`. Each WRITE request was 96 bytes, and all 11 responses returned SMB success.

Two complete SCM waves were identified across the same six destinations. Each destination showed the sequence of manager open, service creation and service start, correlated by TCP stream and DCE/RPC call ID.

The first wave created `WinHostSvc` using a command-interpreter binary path. All six service-creation responses returned `WERR_OK`, while all six service-start responses returned request-timeout errors.

The second wave created `WinUpdateSvc` using a binary located in the Windows Temp directory. All six service-creation and service-start responses returned `WERR_OK`.

The repeated multi-host activity, operation sequence, SMB file operations and closely grouped timing support an inference of coordinated or automated remote activity.

**Final verdict: Suspicious remote service execution and lateral movement observed — escalate to L2 for validation.**

The available network evidence does not establish authorization, operator identity, successful endpoint execution, persistence or confirmed compromise. Endpoint telemetry and authorization records are required to determine the actual impact and legitimacy of the activity.
